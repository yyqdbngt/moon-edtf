## 项目名称

Moon EDTF（MoonBit 模块 `yyqdbngt/moon_edtf`，版本 0.1.0）

## GitHub 地址

https://github.com/yyqdbngt/moon-edtf

## 简介

纯 MoonBit 实现的 EDTF（Extended Date/Time Format）明确子集解析库。它解析并校验精确日期、不确定/近似修饰、掩码年份、区间与选择集合，并对批量输入给出诊断。设计的重点不是把日期换算成时间戳，而是保留“约 1984 年”“19XX 年”“开放端点”这类原始不确定语义——绝不把不确定值静默变成精确日期。零第三方依赖。

## 方向与通用性

属于“数据与内容工具”方向的日期数据清洗基础库。它以库形态交付，不绑定任何业务系统或元数据规范；凡是需要接收、校验、规范化历史或不完整日期文本的 MoonBit 程序都可嵌入使用，因此可复用于档案、博物馆、科研元数据等不同领域。

## 预期使用场景

1. **历史档案整理**：档案目录的日期字段中常出现 `1984?`、`19XX`、`../1984` 这类写法。导入流程逐条调用 `parse` / `normalize` 做校验与规范化，把不合格记录连同错误码和 UTF-16 偏移退回给人工修正，而不是替它补成某个精确年月日。
2. **博物馆藏品年代**：藏品年代描述先由人工转换为受支持的 EDTF 形式，再用 `diagnose_batch` 做批量校验，一次拿到每条记录的规范化值与错误清单，用于质量报告；本库不负责自然语言到 EDTF 的转换，也不猜测年代。
3. **科研不完整日期清洗**：观测记录与文献元数据里混有未知端点、开放区间和选择年份。批量诊断会明确区分空端点（Unknown）与 `..`（Open）、区分选择集合内的 `a..b` 范围与斜杠区间，保留这些区别而不把它们压成一条连续时间区间。

## 核心功能

精确日期 `YYYY`、`YYYY-MM`、`YYYY-MM-DD`，支持负年份与超过四位的年份（须带 `Y` 前缀，如 `Y10000`）；季节 `YYYY-21` 至 `YYYY-24` 作为文档化扩展；修饰符 `?`（不确定）、`~`（近似）、`%`（两者），按“作用于该组件及其左侧组件”的语义传播并保留；掩码低位年份 `199X`、`19XX`，序列化时保留掩码而不臆造 `1990`；区间 `start/end`，其中 `..` 为 Open、空侧为 Unknown，两者保持区分；选择集合 `[1667,1668]` 与集合内范围 `[1667,1668,1670..1672]`；批量诊断 `diagnose` / `diagnose_batch` 返回 valid、稳定错误码、原始偏移与规范化值；`compare` 仅对完整、无修饰的精确日期排序，其余情况显式抛 `Unsupported`。

## 技术路线

UTF-16 游标递归下降解析，类型化模型区分精确、不确定、近似、掩码、Open 与 Unknown 端点，并在模型中单独表示集合内的 `Range`。月日边界会校验：精确年份按格里高利闰年规则校验 `02-29`；掩码年份下闰年状态未知，因此放行 2 月 29 日但仍拒绝 2 月 30 日与 4 月 31 日。错误类型 `EdtfError` 含 `Syntax` 与 `Unsupported` 两类稳定错误码，错误值不回显输入文本。测试覆盖解析、校验、修饰与掩码、区间与端点、选择集合、往返语义、诊断与受限比较。CI 在 wasm / wasm-gc / js / native 四后端执行格式化检查、构建、测试与示例运行。

## 明确不做的范围

不做自然语言日期识别；不做完整历法或时间轴展开；不把不确定、近似或掩码值转换为精确时间戳；不支持时间与时区语法、掩码月/日、嵌套集合、集合内的开放或未知端点、逐组件前缀修饰、花括号全成员集合；不支持集合内的斜杠区间；不声称符合任何完整的 EDTF 一致性等级（包括 Level 0）。`compare` 不做部分日期排序。对外构造器可以表示非法组合，因此校验仍须经 `parse`。

## 原创 / 参考来源与许可证

本项目为独立原创的 MoonBit 实现，许可证 Apache-2.0。格式规范依据 Library of Congress 的 EDTF 规范（https://www.loc.gov/standards/datetime/edtf.html ）。未移植任何第三方解析器，未复制其源码或测试夹具。工程结构参考了本人另一个项目 [Moon JSON Repair](https://github.com/btlqql/moon-json-repair)（Apache-2.0）的仓库组织方式，但未复制其功能逻辑。生态中的相邻项目：MoonCakes 上的 `brickfrog/tempo`（https://github.com/brickfrog/tempo ，Apache-2.0）等精确日期库。本项目与它们相邻而非替代。查重基于 MoonCakes 与 GitHub 的关键词检索，检索未命中不等于绝对没有同类实现。

## 真实需求

历史人文数据与科研元数据中的日期天生不精确：“约某年”“19 世纪”“年代不详”“到某年为止”。通用精确日期库与时间戳模型无法安全表达这类语义——一旦转换成具体日期，不确定性就被抹掉了，而原始信息不可恢复。按 EDTF 标准建模并保留掩码、修饰与开放端点的库，能让清洗流程在“可校验”和“不丢失不确定性”之间兼顾。

## 生态差异

与 `brickfrog/tempo` 这类日期库相比，本项目的差异是定位而非覆盖面：那些库面向精确日期时间的运算、格式化与时间线计算，而本项目专注于 EDTF 文本子集的解析、不确定语义的保留与批量诊断，并明确拒绝把部分日期强行排序。与通用容错日期解析相比，本项目不猜年份、不猜月份，遇到不认识的写法直接给出稳定错误码，把决定权交回调用方。我不声称这是首个或唯一的 MoonBit EDTF 实现。

## 本人对方案的理解

我理解这个项目的核心约束是“宁可拒绝，也不臆造”：不确定、近似、掩码、未知与开放这几种语义必须在内部模型里可区分，并在序列化时保持住，否则整个库就失去意义。所以我宁愿把支持子集划得很窄并逐条写进文档，也不去实现无法保证语义正确的花哨语法；`compare` 只支持完整精确日期，部分日期一律报 `Unsupported`，因为给“约 1984 年”和“1984 年”排出先后本身就是错的。测试上我特别关注往返语义——合法输入规范化后再解析必须保持同一语义。
